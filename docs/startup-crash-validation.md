# 默认三维启动计算闪退：修复与验证

日期：2026-11-23。用户确认现象为直接退出、3D、其他设置默认。适用当前源码启动器；历史便携附件没有覆盖。

## 可重复证据

读取当日三份 Python 原生转储的异常流与模块信息，出现 0xC0000409 和 0xC0000374（堆损坏），栈中包含 VTK、Qt、CuPy FFT 缓存。没有将完整转储提交仓库，也没有将普通参数错误与原生退出混为一谈。

独立解释器启动默认 3D，先完成 256 自动预览，再点击等效的完整计算（1024、自动后端，实际 CUDA），触发相同退出。首次记录退出码 -1073740940，增加线程追踪后为 -1073741819；faulthandler 显示三维更新附近的原生访问冲突。线程记录确认三维更新在主线程，CuPy 缓存回收来自计算线程。

| 对照 | 结果 |
| --- | --- |
| 修复前：默认 3D、预览后完整自动 CUDA | 已复现闪退 |
| 修复前：关闭自动循环 GC | 仍闪退，后台有显式 gc.collect |
| 修复前：CPU，三次 1024 完整计算 | 通过、退出 0 |
| 修复后：保持 3D 和 CUDA，三次 1024 完整计算 | 通过、退出 0 |

原始本机诊断在忽略目录 `outputs/reproduce-start-crash.log`、`reproduce-start-thread-trace.log`、`reproduce-no-auto-gc.log`、`reproduce-cpu-control.log`、`reproduce-cache-pin.log`。

## 修复机制

CuPy 14.2 的每线程 FFT 缓存在析构清理链表时显式执行全局循环回收；在计算线程退出时，这可能把三维 Python/VTK 资源也放到后台回收，与界面生命周期冲突。仅禁用自动 GC 无法阻止此显式调用，普通 Python try/except 也不能恢复已经损坏的原生堆。

应用层现在在 Job 的 finally 持有 FFT 缓存，包含成功、取消和异常路径。完成信号使用 Qt 队列和 Slot；任务 finished 回调、替换旧任务、关闭窗口均等待线程真正退出，再在主线程、相同 CUDA 设备上下文清理。Qt 的 finished 信号不保证线程局部析构已结束，所以保留 wait。未修改第三方库，未永久关闭 GC，也未降低网格或禁用 CUDA/3D。来源见 [调研记录](research.md)。

## 回归方法与范围

新增 `scripts/validate_startup_crash.py`。从新解释器运行：

```powershell
.\.venv\Scripts\python.exe -X faulthandler scripts/validate_startup_crash.py --output outputs/startup-check.json --runs 3
```

它先建立真实三维场景与默认预览，再启动首次及重复 1024 完整计算，记录实际后端、场景是否引用当前结果、缓存是否释放及释放线程。测试结束关闭自己创建的窗口；出现报错、原生退出或超时均不能算通过。没有 GPU 的机器会由硬件测试明确跳过，不能伪称完成 CUDA 验证；本机新增测试实际执行 CUDA，无跳过。

新增冷启动回归 1 项通过（10.18 s），包括三次实际 CUDA 完整计算、三次主线程缓存释放；另有模拟成功、取消、内存不足与普通异常的缓存生命周期专项 1 项通过（4.92 s）。之前 166 项通过没有覆盖这种“先建三维、再首次在任务线程启用 CUDA”的启动顺序，本轮明确补齐。

这份验证针对已经复现的故障与本机软硬件，不代表任意显卡、驱动、显存不足场景或所有原生异常的恢复保证。原生异常仍应通过独立进程、系统转储和实际退出码调查。

最终完整回归 **168 项通过、0 跳过**（77.81 s），包含原有 7 项真实 CUDA 对照与新增独立进程启动测试；后者再次完成三次实际 CUDA 计算。干净提交快照文档/中文规范 18 项通过（1.10 s），规则脚本和差异检查通过。CuPy 有 CUDA_PATH 未检测提示，但本机实际 GPU 测试成功。
